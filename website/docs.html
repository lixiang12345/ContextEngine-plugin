ContextEngine 使用手册

面向 AI 编程 Agent 的可移植、Augment 级代码库上下文引擎。本手册覆盖从安装到生产部署的完整路径，对应 contextengine-plugin v0.5.0。

它是什么

ContextEngine 是一层小而完整的检索组件：把 PostgreSQL 全文检索、符号表、路径匹配、pgvector 语义向量、import/symbol 依赖图与提交历史融合成一次检索，再按 token 预算打包为带路径与行号的上下文，交给编程 Agent 使用。

query ──► 查询理解 ──► FTS / 符号 / 路径 / 向量 并行召回
                          │
                          ▼
              RRF 融合 ──► 特征重排 ──► (可选)神经重排
                          │
                          ▼
              依赖图扩展 ──► MMR 多样性打包 ──► Agent / MCP

四种形态

  • MCP 服务器(stdio) — 接入 Claude Code、Cursor 等任何 MCP 客户端；
  • CLI — index / search / context / status 等命令，适合脚本与 CI；
  • HTTP 服务 — Bearer 鉴权的工作区同步、后台索引任务、Remote MCP 与运维仪表盘；
  • TypeScript 库 — 嵌入你自己的 Agent 循环。

没有 embeddings 也能用。不配置任何 API key 时，引擎以 BM25-only 模式完全离线运行；配置 OpenAI 兼容 embeddings 端点后自动升级为混合语义检索。

安装

环境要求

  • Node.js ≥ 22.5
  • 带 pgvector 扩展的 PostgreSQL(仓库内置本地 Docker Compose，pgvector 由引擎自动启用)

从源码安装(推荐)

git clone https://github.com/lixiang12345/ContextEngine-plugin.git
cd ContextEngine-plugin
npm install
npm run build
npm link   # 可选：全局暴露 contextengine / contextengine-mcp / contextengine-http

npm link 之后，三个可执行入口在任何目录可用：contextengine(CLI)、contextengine-mcp(MCP stdio)、contextengine-http(HTTP 服务)。

作为库安装

npm install contextengine-plugin
import { ContextEngine } from "contextengine-plugin";

const engine = ContextEngine.open({ root: process.cwd() });
await engine.index();
const hits = await engine.search({ query: "auth middleware" });

免安装试用

npx contextengine-plugin index
npx contextengine-plugin search "stripe payment webhook"

快速开始

第 1 步：准备 PostgreSQL

在仓库目录启动内置的本地 pgvector 服务(仅需一次)，并导出连接串：

npm run db:up
export CONTEXTENGINE_DATABASE_URL=postgresql://contextengine:contextengine@127.0.0.1:54329/contextengine

索引数据全部存在 PostgreSQL 中，以工作区绝对路径为命名空间——同一个数据库可以安全容纳多个仓库，且不会把向量整体加载进进程内存。CONTEXTENGINE_DATA_DIR 仅用于定位待迁移的遗留 SQLite 索引。

第 2 步：建索引

contextengine index              # 索引当前目录
contextengine index /path/to/repo   # 或指定仓库路径

第 3 步：搜索与打包

# 混合搜索(默认 auto 模式)
contextengine search "how is rate limiting implemented"
contextengine search "processPayment" --mode bm25 -k 5

# 为一个开发任务打包上下文(给 Agent 用)
contextengine context "Add retry logic to the payment webhook"

# 查看索引状态
contextengine status

搜索结果始终携带路径 + 行号区间，打包结果附带检索轨迹(intent、参与通道、token 用量、索引 generation)——这是"Agent 原生“而非”聊天原生"的设计：所有证据可直接定位、可复核。

CLI 参考

全部命令一览：

contextengine index [root] [--quiet] [--exclude <glob...>]
contextengine search <query> [-k N] [--mode auto|bm25|semantic|hybrid] [--path-prefix p] [--json]
contextengine context <task> [--max-tokens N] [--json]
contextengine status
contextengine clear-index
contextengine migrate-sqlite <legacy-index.db>
contextengine watch [root] [--debounce 800]      # 实时增量重建
contextengine serve [--auto-index]               # MCP stdio 服务器
contextengine http [--host 127.0.0.1] [--port 8787]   # 鉴权 HTTP 服务
contextengine ci-template <github|gitlab|bitbucket>   # 输出可安装的 CI 工作流
contextengine snapshot export|import|list|delete|prune|gc [name] [--store path|s3://bucket/prefix]
contextengine eval [--self | --cases file.json] [--reindex]
contextengine profile list|add|use …

index — 建立 / 增量更新索引

对工作区做声明/方法级切块并写入 PostgreSQL。已配置 embeddings 时同时嵌入新增与变更的块。重复执行按文件哈希增量，只处理变化的文件。--exclude 追加排除模式(等价于 CONTEXTENGINE_EXCLUDE 环境变量)。

search — 混合搜索

  • --mode auto(默认)：有 embeddings 则混合，否则 BM25；也可强制 bm25 / semantic / hybrid;
  • -k N：返回条数；--path-prefix：限定路径前缀；--json：结构化输出。

context — 为任务打包上下文

输入一句任务描述，输出经过 MMR 去重、按相关性排序的证据块集合。引擎模型中立：默认返回 topK 选出的全部证据，不猜测模型上下文窗口；调用方明确需要更小载荷时才传 --max-tokens。

watch — 实时增量索引

监听文件变更，防抖(默认 800ms)后增量重建。适合长期开着的本地开发会话。

其余命令

  • status — 文件数、块数、embedding 覆盖等索引统计；
  • clear-index — 清空当前工作区的索引数据；
  • migrate-sqlite — 一次性迁移 0.3.x 时代的本地 SQLite 索引；
  • serve — 以 stdio 启动 MCP 服务器(详见 MCP 集成);
  • http — 启动鉴权 HTTP 服务(详见 HTTP 服务);
  • ci-template — 打印 GitHub Actions / GitLab CI / Bitbucket Pipelines 的索引刷新工作流模板；
  • snapshot — 团队索引快照(详见 索引快照);
  • eval / profile — 见 评测 与 多仓 Profile。

语义检索

不配置 API key 时，ContextEngine 以 BM25-only 模式运行(依然实用)。配置任意 OpenAI 兼容 embeddings 端点即可启用混合语义检索：

export OPENAI_API_KEY=sk-...
# 可选覆盖：
export OPENAI_BASE_URL=https://api.openai.com/v1
export OPENAI_EMBEDDING_MODEL=text-embedding-3-small

contextengine index    # 为新增/变更块生成向量
contextengine search "checkout timeout" --mode hybrid

同一组配置也接受 ContextEngine 前缀的别名：CONTEXTENGINE_EMBEDDING_API_KEY、CONTEXTENGINE_EMBEDDING_BASE_URL、CONTEXTENGINE_EMBEDDING_MODEL。

兼容 OpenAI 官方、各类代理以及暴露 /v1/embeddings 的本地服务(如 Ollama 兼容网关)。Base URL 写成源站(https://gateway.example.com)或带版本(…/v1)均可，引擎会自动规范化。

contextengine index

降级与保护

  • 每次查询的语义 / 重排阶段各有 2000ms 预算(CONTEXTENGINE_SEARCH_SEMANTIC_TIMEOUT_MS / _RERANK_TIMEOUT_MS)，超时自动回退词法通道，检索不会因模型服务卡住而失败；
  • 模型端点连续失败 3 次后断路器打开，冷却 30 秒(CONTEXTENGINE_SEARCH_BREAKER_FAILURE_THRESHOLD / _COOLDOWN_MS);
  • 所有降级都会体现在响应的检索轨迹里，而不是静默发生。

忽略规则

索引期按以下顺序过滤文件，行为与 Augment Context Connectors 对齐：

  1. 内置智能过滤 — node_modules/、vendor/、dist/、build/、target/、二进制、lock 文件、.env 机密、IDE 杂项等；
  2. .gitignore(根目录 + 嵌套目录规则);
  3. .augmentignore(与 Augment 语义一致，支持 ! 反选重新纳入);
  4. .contextengineignore(产品专属);
  5. CLI / 环境变量 — contextengine index --exclude 'vendor/**' '**/*.generated.*' 或 CONTEXTENGINE_EXCLUDE=…。

示例 .augmentignore:

# 重新纳入某个被 gitignore 的目录
!some-tracked-deps/

# 排除测试夹具 / 本地数据
data/test.json
*.tmp

多仓 Profile

在多个仓库之间快速切换默认工作区：

contextengine profile add app --root ~/work/my-app
contextengine profile add api --root ~/work/my-api
contextengine profile use app
contextengine profile list

配置写入 contextengine.profiles.json(格式见仓库 examples/contextengine.profiles.example.json)。也可以用 CONTEXTENGINE_EXTRA_ROOTS=docs:/path/to/docs 把文档仓、额外目录并入同一个索引，一次检索同时覆盖代码与文档。

MCP 集成

ContextEngine 通过 stdio 说 Model Context Protocol，任何 MCP 客户端均可接入。

Claude Code

# 方式一：指向构建产物
claude mcp add contextengine -- node /absolute/path/to/ContextEngine-plugin/dist/mcp-server.js

# 方式二：npm link 之后
claude mcp add contextengine -- contextengine-mcp

Cursor / 其他 MCP 客户端

添加一个 MCP 服务器条目，把 cwd 设为要索引的工作区(或设置 CONTEXTENGINE_ROOT):

{
  "command": "node",
  "args": ["/absolute/path/to/ContextEngine-plugin/dist/mcp-server.js"]
}

环境变量(可选)

export CONTEXTENGINE_ROOT=/path/to/repo
export CONTEXTENGINE_AUTO_INDEX=1
# MCP 文件监听默认开启；置 0 关闭
export CONTEXTENGINE_MCP_WATCH=1
# 可选：逗号分隔的 alias:path 额外根目录
export CONTEXTENGINE_EXTRA_ROOTS=docs:/path/to/docs
export OPENAI_API_KEY=...

暴露的工具

工具用途
codebase-retrievalAugment 兼容的打包检索(建议 Agent 首先调用;codebase_retrieval 为旧别名)
codebase_search混合搜索 → 路径、行号、符号、内容
get_task_context按 token 预算打包排序后的证据块
get_file_context读取文件 / 行区间
index_status索引统计
reindex_workspace增量重建索引

Agent 使用建议：先调 get_task_context 拿到任务上下文再动手编辑；后续追问用 codebase_search。

MCP 服务器默认监听工作区根与 CONTEXTENGINE_EXTRA_ROOTS，文件变更防抖后增量刷新检索。设 CONTEXTENGINE_MCP_WATCH=0(也接受 false / off / no)可关闭监听；关闭后由 CONTEXTENGINE_AUTO_INDEX=1 决定首次 MCP 请求时是否自动补建缺失索引。

HTTP 服务

同一检索核心以鉴权 HTTP 服务的形式服务远端 IDE 与团队：源文件以内容寻址 Blob 存入 PostgreSQL，客户端只同步变更的哈希，提交工作区修订后观察后台索引任务，再发起查询。

启动

export CONTEXTENGINE_DATABASE_URL=postgresql://contextengine:contextengine@127.0.0.1:54329/contextengine
export CONTEXTENGINE_HTTP_API_KEY="$(openssl rand -base64 32)"

contextengine-http
# GET /health · GET /openapi.json
# 仪表盘: http://127.0.0.1:8787/dashboard
# 所有 /v1 路由使用 Authorization: Bearer <key>

核心端点：工作区创建 / 列表、/sync/plan、PUT /blobs/{sha256}、/sync/commit、/index-jobs(SSE 进度)、/search、/context、/file。完整客户端契约、载荷与 IntelliJ 插件映射见 docs/HTTP_API.md。

Remote MCP(Streamable HTTP)

支持 MCP 的远端客户端可直接使用 /v1/workspaces/{workspaceId}/mcp，携带同一个 Bearer key。首个请求为 initialize，返回 mcp-session-id；后续请求即可调用该工作区的 codebase-retrieval 工具。会话元数据持久化在 PostgreSQL，可在任意健康实例上恢复、经受进程重启，无需粘性路由。该 JSON 响应模式支持 POST 与幂等 DELETE;GET/SSE 返回 405(实时流不可重建)。

运维仪表盘

HTTP 服务自带 /dashboard(与 /v1/* 同一 Bearer key)，展示：

  • 工作区修订、已索引文件、块数与 embedding 状态；
  • 近期索引任务与进度；
  • 按路由的请求量、错误率、平均与 p95 延迟；
  • 进程运行时长与内存；
  • 对已索引工作区的在线检索探针。

观测数据只含方法、规范化路由、状态码与延迟；查询文本、源码内容、请求体与 API key 一概不采集。仪表盘轮询同源 GET /v1/observability/overview，无需单独的前端构建。

Docker Compose 部署

export CONTEXTENGINE_HTTP_API_KEY="$(openssl rand -base64 32)"
docker compose up -d --build
docker compose ps
# 仪表盘默认发布在 http://127.0.0.1:8790/dashboard(仅绑定回环地址)

仅在可信的远程部署中设置 CONTEXTENGINE_DOCKER_HTTP_BIND_HOST=0.0.0.0。PostgreSQL 与运行时数据使用命名卷，普通 docker compose down 保留索引数据；只有确认要删除数据库时才用 down -v。

鉴权、ACL 与连接器

  • 多主体鉴权 — 多把 Bearer key(CONTEXTENGINE_HTTP_API_KEYS)或经验证的 OAuth/OIDC JWT(CONTEXTENGINE_OIDC_ISSUER)，按工作区实施 reader / writer / owner 权限；OIDC 主体跨 token 轮换保持稳定，仅服务端配置的组映射可授予 operator；
  • 源策略 — owner 可设默认允许/拒绝 + 嵌套路径前缀规则，search / context / 文件读取 / Remote MCP 统一强制执行；
  • 只读连接器 — GitHub、GitLab、Bitbucket Cloud 与静态网站连接器把外部内容挂到空 Blob 工作区并增量同步；网站爬虫强制 HTTPS/公网、同源、路径前缀、robots、重定向、页数、深度与字节数限制；
  • Webhook 与 CI — 签名的 GitHub / GitLab push webhook 幂等触发同步；source 级 CI trigger token 让流水线只刷新单个源，而无需工作区级 API key(模板见 contextengine ci-template)。

Library API

TypeScript 类型完整，适合把检索嵌入你自己的 Agent 循环：

import { ContextEngine } from "contextengine-plugin";

const engine = ContextEngine.open({ root: "/repo" });

// 建索引(带进度回调)
await engine.index((p) => console.log(p.phase, p.filesDone));

// 统计
const stats = await engine.stats();

// 搜索
const hits = await engine.search({ query: "…", topK: 8, mode: "auto" });

// 为任务打包上下文
const packed = await engine.getTaskContext({
  task: "…",
  // 可选的调用方传输上限: maxTokens: 16_000,
});

await engine.close();

检索输出模型中立：引擎按 topK 完成检索、重排、去重与格式化，不检查模型名或上下文窗口大小；只有调用方明确需要更小载荷时才传 maxTokens。嵌入式宿主还可以通过 connectorPlugins 注册额外的内容源提供方(契约见 docs/PLUGINS.md)。

连接器与 webhook 相关变量(CONTEXTENGINE_GITHUB_TOKEN、CONTEXTENGINE_GITLAB_TOKEN、CONTEXTENGINE_BITBUCKET_TOKEN、webhook 签名密钥等)见 HTTP API 指南。

索引快照

活跃的索引 generation 可以打成版本化、校验和验证的快照，经文件系统或 S3 兼容存储在团队间分享——新人不必重复整仓索引。

contextengine snapshot export my-repo --store /shared/ce-snapshots
contextengine snapshot list        --store /shared/ce-snapshots
contextengine snapshot import my-repo --store s3://bucket/prefix
contextengine snapshot prune | gc  # 清理旧版本 / 垃圾回收

配置 CONTEXTENGINE_SNAPSHOT_STORE 后，同样的快照操作(导出、导入、prune、GC)通过 HTTP 服务暴露给 owner，返回持久的 PostgreSQL 任务记录，支持轮询与 SSE 状态；还可配置间隔制或时区感知的每日复制调度，带吞吐、滞后与有界失败告警。CLI 快照命令保持同步语义。详见 docs/SNAPSHOTS.md。

评测

质量不是一句口号：仓库自带 Recall / MRR / nDCG 指标、PR 级配对评测与多语言基准，全部可本地复现。

# 内置用例，对本仓库自评
contextengine eval --self --reindex

# 自定义用例
contextengine eval --cases examples/eval.sample.json --root /path/to/repo

# 多语言 OSS 套件(需要 embeddings 端点)
npm run bench:multilang

# 远程 API 冒烟基准：10 查询语言 × 10 代码语言
npm run bench:api

# 多仓中型套件(克隆到 /tmp/ce-bench)
node scripts/bench-suite.mjs

PR 级配对评测

contextengine eval-pr \
  --manifest /path/to/pr-suite.json \
  --allow-exec \
  --out eval-results/pr-suite.json \
  --markdown eval-results/pr-suite.md

# 固定 corpus 的 CI oracle 门：base 必须失败、gold 必须通过(不调用 Agent)
npm run eval:pr:corpus:validate

manifest 中的命令需要 --allow-exec 显式授权才会执行；运行完整 corpus 前请先审阅 manifest 内容。诚实说明：公开 corpus 结果、受控真实模型运行与 Augment 可比的质量结论尚未发布。

方法学与多仓套件报告见 EVALUATION.md;PR 评测框架见 docs/PR_EVAL.md;embedding 模型选型见 docs/EMBEDDINGS.md。

故障排查

启动即报数据库错误

CONTEXTENGINE_DATABASE_URL(或 DATABASE_URL)是必填项。本仓库内可执行 npm run db:up 启动内置 pgvector 服务，再导出 postgresql://contextengine:contextengine@127.0.0.1:54329/contextengine。pgvector 扩展由引擎自动启用，无需手工 CREATE EXTENSION。

Node 版本报错

要求 Node.js ≥ 22.5(package.json 的 engines 字段有硬性声明)。用 node -v 确认，必要时通过 nvm / fnm 升级。

语义搜索超时或变慢

  • 每次查询的语义 / 重排预算默认各 2000ms，超时自动回退词法结果——功能不中断，但排名可能变化；结果 trace 中会标注降级通道；
  • 连续失败 3 次后断路器打开、冷却 30 秒，期间跳过模型调用；
  • 检查 OPENAI_BASE_URL 是否可达；写源站或 /v1 形式均可，引擎会规范化。

某些文件没有被索引

  • 先核对五层忽略规则(内置过滤 → .gitignore → .augmentignore → .contextengineignore → --exclude);
  • 超过大小上限的文件会被跳过：默认 512 KiB，可用 CONTEXTENGINE_MAX_FILE_BYTES 调整(硬上限 32 MiB);
  • 被 .gitignore 排除但确需索引的路径，在 .augmentignore 中用 !path/ 反选纳入。

MCP 客户端搜不到结果

  • 确认 MCP 服务器的 cwd 或 CONTEXTENGINE_ROOT 指向正确工作区；
  • 设 CONTEXTENGINE_AUTO_INDEX=1 让首次请求自动建缺失索引，或先手动跑 contextengine index;
  • MCP 进程同样需要 CONTEXTENGINE_DATABASE_URL 环境变量。

HTTP 请求返回 401

所有 /v1 路由都要求 Authorization: Bearer <key>，key 即 CONTEXTENGINE_HTTP_API_KEY(或 CONTEXTENGINE_HTTP_API_KEYS 中的某一主体)。仪表盘使用同一把 key。

从 0.3.x 升级后找不到旧索引

0.4 起索引存储迁移到 PostgreSQL。旧的本地 SQLite 索引执行一次性迁移：contextengine migrate-sqlite <legacy-index.db>(CONTEXTENGINE_DATA_DIR 仅用于定位旧文件)。

常见问题

不配置 embeddings 能用吗？

能。BM25-only 是一等公民模式：PostgreSQL FTS + 符号 + 路径 + 依赖图 + MMR 打包全部可用，且完全离线。embeddings 是“升级项”而不是前置条件。

支持哪些 embedding 服务？

任何暴露 OpenAI 兼容 /v1/embeddings 的端点：OpenAI 官方、各类代理、本地网关(如 Ollama 兼容层)，以及自托管方案。生产验证过的自托管栈是 Qwen/Qwen3-Embedding-0.6B + 可选 Qwen3-Reranker-0.6B，合计约 2.2 GB 显存。

我的代码会离开本机吗？

索引与向量全部存在你自己的 PostgreSQL 里；只有启用外部 embeddings API 时，待嵌入的代码块文本才会发往你配置的端点(自托管端点则完全不出内网)。HTTP 服务的观测数据不采集查询文本与源码内容。

和 Augment 是什么关系？

没有从属关系。ContextEngine 是独立的开源组件，对齐的是 Augment Context Engine 的系统模式与生态兼容性(codebase-retrieval 工具名、.augmentignore 语义)，并公开维护一份诚实的差距对比——不声称全面对齐。

怎么同时管理多个仓库？

三个机制可组合：同一 PostgreSQL 按工作区绝对路径天然隔离多仓；contextengine profile 快速切换默认工作区；CONTEXTENGINE_EXTRA_ROOTS 把文档仓 / 额外目录并进同一个索引联合检索。

支持哪些编程语言？

多语言 chunker 覆盖主流语言；公开基准跑了 TypeScript、JavaScript、Go、Python、C、C++、Java、Kotlin、Rust 共 10 个真实 OSS 仓库(见基准数据)。词法与符号通道对任何文本语言都有效。

如何在 CI 里自动刷新索引？

contextengine ci-template github|gitlab|bitbucket 输出可直接安装的工作流模板；HTTP 部署可用签名 push webhook 自动同步，或为流水线签发 source 级 CI trigger token——只允许刷新单个源，不暴露工作区级 API key。

索引多大？建一次要多久？

按文件哈希增量：首次全量后，日常重建只处理变更文件；watch / MCP 模式防抖后自动增量刷新。中型 OSS 仓库(数百到数千文件)的索引与检索延迟均在基准脚本 npm run bench:suite 中可自行复现。
